1. AI Trust Layer — co właściwie robi?

To nie pojedynczy model AI. To zestaw mechanizmów platformowych pośredniczących między funkcjami UiPath a modelami językowymi i pomagających kontrolować wykorzystanie AI.

2. Co dzieje się z pojedynczym żądaniem?

Przykład: agent ma podsumować zgłoszenie, a organizacja korzysta z firmowego deploymentu Azure OpenAI. Włączone guardrails mogą dodać osobne kontrole przed i po odpowiedzi.

Technicznie: routing i governance bazują na konfiguracji; skanowanie treści może wywołać odrębną usługę AI. Nie każdy prompt jest automatycznie sprawdzany przez wszystkie możliwe guardrails.

3. Model routing — do czego służy?

Routing wybiera drogę żądania na podstawie mapowania produktu/funkcji, modelu oraz dozwolonych regionów. Nie należy zakładać, że standardowo sam analizuje treść promptu i wybiera „najmądrzejszy” lub „najtańszy” model.

Gdzie to konfigurujesz?

Admin → AI Trust Layer → Model hub (mapowania i regiony) oraz LLM configurations (własne połączenia).

Co jeśli własny LLM nie działa?

Niektóre produkty mogą użyć fallback do modelu UiPath-managed. Jeśli to niedozwolone, trzeba osobno zablokować modele UiPath-managed polityką.

Data residency: ograniczenie do Europy dotyczy regionów routingu modeli objętych daną polityką. Nie zastępuje audytu wszystkich pozostałych usług, logów, konektorów i przechowywania dokumentów.

5. Własny Azure OpenAI: czy dane „zostają u nas”?

Firma może kontrolować miejsce inferencji głównego modelu, korzystając z własnego Azure OpenAI. Ale w architekturze SaaS żądania przechodzą również przez usługi UiPath, a przy aktywnych guardrails także przez odpowiednie usługi kontroli bezpieczeństwa.

Nie mów bez dodatkowych ustaleń: „Żadne dane nie opuszczają infrastruktury firmy”.
Bezpieczniejsze sformułowanie: „Inferencja głównego LLM jest realizowana w naszej subskrypcji Azure; ruch jest pośredniczony przez UiPath AI Trust Layer zgodnie z konfiguracją i politykami”.

Trzeba osobno sprawdzić: gdzie znajduje się główny endpoint, czy aktywne guardrails odsyłają treści do innych usług, gdzie zapisują się logi i ślady, w jakim regionie powstają indeksy wiedzy oraz czy fallback jest dozwolony.

6. Audit, observability i Context Grounding

Audit / usage

Informacja o tym, kto, kiedy i z jakiego produktu wywoływał LLM; dostępne mogą być metadane modelu oraz treści wejścia i wyjścia.

Kluczowa polityka: Enable prompts saving for Audit? — ustawienie No wyłącza przechowywanie treści promptów/odpowiedzi w tym audycie.

Nie gwarantuje wyłączenia wszystkich pozostałych logów, np. agenta lub procesu.

Context Grounding / RAG

Dokument → indeks i embeddingi → wyszukiwanie trafnych fragmentów → kontekst do LLM.

Istotne: to odrębna usługa od routingu modelu. Własny LLM nie przenosi automatycznie indeksu wiedzy do firmowego Azure.

Context Grounding nie jest uniwersalną gwarancją poprawności. RAG pomaga oprzeć odpowiedź na danych, lecz nadal trzeba oceniać trafność źródeł i zgodność odpowiedzi z dokumentem.

7. Lista pytań do architekta / działu Security

  • Jaki model i deployment faktycznie obsługuje każde wywołanie? Czy Model Hub pokazuje oczekiwane mapowanie?
  • Czy fallback do UiPath-managed LLM jest wyłączony, jeśli polityka firmy tego wymaga?
  • Jakie guardrails są faktycznie włączone i którym dostawcom przesyłają dane?
  • Jakie regiony przetwarzania i przesyłania ruchu są dopuszczone?
  • Czy zapis treści promptów/odpowiedzi w Audit jest zgodny z polityką retencji?
  • Gdzie są przechowywane dokumenty, indeksy i embeddingi Context Grounding?
  • Czy istnieje test potwierdzający ścieżkę: Agent → Trust Layer → firmowy Azure → odpowiedź?
  • Czy przeglądane są także Execution Traces, logi robota, Action Center i konektory?

Szybka analogia do wykorzystania na warsztacie

Gateway = brama, routing = adresowanie, governance = przepisy organizacji, guardrails = kontrola zawartości, audit = dziennik zdarzeń, Context Grounding = biblioteka wiedzy. Nie wszystkie te mechanizmy używają AI.
